# Context

Decision 010 made the provider list an operator-editable YAML catalog (the allowlist of vendors that may receive prompts) and nine vendor adapters existed in code. Every vendor call was paid with one operator-held key, read by name from the gateway's environment. Organizations are different companies: their spend landed on a platform account and one leaked key would have exposed all of it. The owner decided on 2026-11-06 that the list is a constant with one production provider, Claude Code, and that every organization supplies, pays for and controls its own Claude API key. The full spec is `.claude/thoughts/investigations/2026-11-06-org-claude-key-and-fixed-provider.md`; this record keeps the choices and why.

# Decision

1. **The catalog becomes a fixed list in code.** `providers/gru_providers/fixed.py` holds the constant: `claude-code` in every environment, plus `echo` only when `GRU_ENV=dev`. This reverses the operator-editable part of decision 010; its intent (a closed allowlist, fail closed) stands, as a constant a code change and a decision record must touch. `claude` is an alias of `claude-code` (a task stored before the change still starts and still passes the gateway). `backend` on a task or run is optional and defaults to `claude-code`; any other name is a 400 `unknown backend`. The models (four) and their prices (micro-USD per million tokens) are constants too; there are no organization-level overrides. The prices are read from text with `Decimal`. `fixed.py` records that they were checked against the vendor's price page on 2026-11-06; the owner confirms them again before production (a price that is too low lets a budget overshoot).
2. **One provider, a runner chosen by rule.** Chat tasks and review stages run on `gru-agent` (the `anthropic` SDK adapter); every other stage runs the pinned Claude Code CLI; `echo` runs on `gru-agent`. Both go through the gateway with the organization's key. The provider's `runner` in `GET /v1/providers` is `claude-code` (the UI uses it for the skills picker). Rejected: Claude Code CLI only (chat and review stages would need rebuilding or removing) and keeping the catalog with one entry (an editable file stays, against the direction).
3. **A Claude API key per organization, never platform-wide.** Saved on `PUT /v1/organization/llm-key`, shown once at save (never again: status, last four characters, date and who set it), checked with Anthropic first (`GET /v1/models`: refused is 400 `invalid_llm_key`; unreachable, 429 or 5xx is 503 `llm_key_unchecked`; nothing is stored in either case), audited (`llm_key.set`, `llm_key.removed`, field name `llm_key`, never a value) and never in an MCP result, log line, metric, error or the Task spec. The sandbox gets only its per-task gateway token. A `ILlmKeyResolver` gives the gateway the key on every call (never cached, so a replaced or removed key takes effect on the next call in every replica).
4. **Sealed with the organization's own data key, wrapped by Cloud KMS.** Each save generates a fresh random 32-byte data key, seals the Claude key with AES-256-GCM (12-byte nonce, authenticated data `b"gru-llm-key\0" + organization_id`) and stores the data key only wrapped (KMS `encrypt` with the same bytes as additional authenticated data), in `org_llm_keys` (migration `0024`). The sealer's method is `unseal` (a domain test rejects the text `open(`). `GRU_SECRETS_KMS_KEY` names the KMS key; gru-api's service account needs `roles/cloudkms.cryptoKeyEncrypterDecrypter` on it. Unwrapped data keys are cached in memory only (bounded, 5 minutes). A row copied to another organization does not open; deleting an organization's row destroys its only wrapped data key. Rejected: one master key from Secret Manager (first choice, withdrawn: one leak opens every company's key) and one Secret Manager secret per organization (per-organization lifecycle, API calls and IAM). No key that opens every organization's key exists in the environment, a file or Secret Manager. The KMS key is still a root of trust, so the permission goes to gru-api's service account alone and every use is in the KMS audit log.
5. **KMS failures are told apart.** A transient failure, a wrong KMS key name or a refused `encrypt` is loud: saving answers 503 and a gateway call is refused as unavailable with nothing reserved. A destroyed key version, a bad checksum or a failed authentication tag is "no key": the gateway refuses `gru_no_api_key` and the status shows not configured, so the organization enters its key again.
6. **Refuse early and again late.** Submitting a task or starting a run with no key answers 400 with a sentence telling an owner where to add it, and nothing is created. The gateway refuses again, with a vendor-shaped 403 `gru_no_api_key` and no reservation, for a key removed mid-run, so a running task fails with that message. `echo` is exempt. Budgets, run budgets and the monthly cap stay as they were: they now limit the organization's spend on its own bill.
7. **Who may change the key (amended 2026-11-06).** Only an owner of the organization, or a platform operator (a Gru admin, directly or acting for the organization with `X-Gru-Act-As-Org`), sets, replaces or removes it; an admin, a member and an API key cannot (403). Operator changes are audited under the organization. Any member and any operator can read the status, so the New run page can warn. This is an explicit exception to the CLAUDE.md rule that every new configuration area is a `GrantArea`, by the owner's decision of 2026-11-06: the organization pays for and controls the key, so access cannot be lent with a grant. It is not synced through GitOps (CLAUDE.md rule 1, answer no: a secret).
8. **Dev seam.** `echo` and `GRU_ANTHROPIC_BASE_URL` (points the fixed provider and the key check at the fake vendor) exist only when `GRU_ENV=dev` and are refused in staging and prod, as is `GRU_SECRETS_KMS_ENDPOINT` (points the real KMS client at the floci-gcp emulator already in the k3d cluster; verified to support symmetric encrypt and decrypt with authenticated data). `make api-up` creates the dev key ring and key in floci. floci's state is lost when its pod restarts and a recreated dev key cannot open rows wrapped by the old one, so dev organizations enter their key again. Unit tests and `--fake` use an in-process wrapper built in code, never selected by configuration; `--fake` accepts an `api_key` in its mint seam. `GRU_PROVIDERS_FILE` is retired: nothing reads it (beta, no compatibility, so no refusal message).

**Amended 2026-11-06 ([decision 033](/decisions/033-no-fake-vendor.md)).** `GRU_ANTHROPIC_BASE_URL` and the dev fake vendor are removed from the running system; the key check always goes to Anthropic and dev needs a real key. Point 8's text above is the history; only `echo`, `GRU_SECRETS_KMS_ENDPOINT` and the in-process wrapper remain as dev seams.

# Consequences

- Frozen-surface changes approved by the owner on 2026-11-06: the routes `GET|PUT|DELETE /v1/organization/llm-key`; migration `0024_org_llm_keys` (additive); the audit actions `llm_key.set` and `llm_key.removed` (31 and 32); the gateway refusal `gru_no_api_key`; `backend` optional with `claude` as an alias and every other name refused; `allowed_providers` retired (accepted and ignored, the settings return the fixed list; the column stays until a later `_contract` revision); `GET /v1/providers` and `list_providers` return the fixed list; `GRU_PROVIDERS_FILE` retired; new variables `GRU_SECRETS_KMS_KEY`, and dev-only `GRU_SECRETS_KMS_ENDPOINT` and `GRU_ANTHROPIC_BASE_URL`; the removal of the YAML catalog, `default.yaml`, the eight other vendor adapters and the `openai` and `any-llm-sdk` dependencies. No MCP tool was added (the 61 names are unchanged); `get_organization_settings` shows one status line.
- Staging and prod need a Cloud KMS key and the encrypt/decrypt grant before the deploy (infrastructure outside this repository, `docs/operations.md`). Rotating the KMS key means a new version, which still unwraps old data keys; destroying a version means organizations enter their keys again.
- Customers' agent spend lands on their own Anthropic accounts, with their own console limits; no customer depends on a platform key, and the platform holds no vendor key to leak.
- Not built: any provider other than Claude (a later one is a code change with its own decision record), subscription or OAuth credentials, organization-level price or model overrides, KMS rotation tooling beyond what Cloud KMS does natively.
- The shipped price table is the owner's to check against Anthropic's prices before production, as is the Claude mark in the UI against Anthropic's brand guidelines.
