# Context

The word "skill" in gru meant a workflow stage's system prompt (`Stage.skill`). Claude Code skills (a directory with `SKILL.md`, optional scripts and references) could not reach a sandbox: the claude-code runner starts the pinned CLI with `HOME=/workspace/.gru-cli`, an empty directory, and the only channels into a sandbox are 16 KiB of environment text and the workspace import. The owner asked for a panel where an organization's admins install, update and configure skills, for the same configuration to live in `<account>/.gru`, and for some skills to be on in every Claude run. The full spec is `.claude/thoughts/investigations/2026-11-05-claude-skills-panel.md`; this record keeps the choices and why.

# Decision

1. **Git-pinned catalog, files held in MySQL.** A skill is `repo@sha` plus a path; install resolves the pin, fetches that tree, validates it and stores a deterministic tar.gz in `org_skills` (migration `0015`, at most 50 skills per organization, 200 files and 2 MiB each). Rejected: fetching from GitHub at task start (the pin can move, GitHub in the hot path, a credential at task time) and baking skills into the task image (every change is an image roll). The sandbox has no network of its own, review needs a fixed commit, and tasks keep working while GitHub is down.
2. **The agent pulls the bundle from the gateway.** `GET /skills/v1/bundle[?names=a,b]` on the gateway listener, authenticated with the task's own `gru_gw_` token (the organization comes from the token), a gzip tar of a sorted `manifest.json` and the skill files, digest in `X-Gru-Archive-Sha256`, at most 8 MiB. The Go runner stays unchanged and no env text is involved. The agent verifies the digest, extracts with path confinement and no symlinks into `<home>/.claude/skills/<name>/`, writes `settings.json` and then starts the CLI; a failed fetch is `error.txt`.
3. **Narrowing is `stage.skills`; per-skill configuration is `mode`.** One narrowing mechanism, on the workflow stage (absent = every enabled skill, `[]` = none, a name that is not installed fails the stage closed), so it is versioned and synced with the workflow. It reaches the agent as `GRU_SKILLS`, set only for the claude-code runner. `mode` (`on`, `name-only`, `user-invocable-only`, `off`) maps to Claude Code's `skillOverrides`. The stage field is `skills`, not `skill`, which stays the prompt.
4. **`hooks` is refused; `allowed-tools` is accepted.** Originally both were refused. Decision 12 of the spec (owner, 2026-11-05) accepts `allowed-tools` for every source: the admin's install is the approval, `inspect` returns the requested tool names (`allowed_tools`, at most 50 of 100 characters), the UI needs an explicit tick before Install, MCP `install_skill` has no tick (an MCP call is the admin's explicit act), and the audit event keeps ids and field names only. `hooks` stays refused because it runs commands on tool events, a different power. Skills always run with `disableSkillShellExecution: true`.
5. **Sources are any public repository, or a connected account's repository (amended: the allow-list is no longer consulted).** Anyone who may install (admin, a `skills` grant, GitOps) can install from any public repository, pinned by sha; connected accounts are needed only for private repositories. An owner in the connected scope is read with the installation token, any other owner with no credential (an unrestricted dev scope tries the installation, then the public reader on a not found). Not found says what to do: `<repo> was not found. It must be a public repository, or belong to a GitHub account connected...`, `commit <sha8> was not found in <repo>`. History: Decision 11 of the spec first added a platform-operator allow-list of external owners (`skill_external_owners`, migration `0016`, `/v1/admin/skills/external-owners*`, audit `skill.external_owner_added|removed`); the owner then made every public repository installable and ordered the list removed the same day (2026-11-05), so it was never released: the routes, the audit actions and the UI section are gone and migration `0020_skill_owners_contract` drops the table. The unauthenticated read is at GitHub's 60 requests per hour per IP and about N+5 requests for a skill of N files, an operator caveat; a limit hit is a fixed `Transient` sentence. Anything else is a 400 and nothing is stored.
6. **GitOps keeps the pin, never the files.** `skills/<name>.yaml` holds `version`, `name`, `source` (`repo`, `path`, `ref`, required `sha`) and `mode`. A pushed manifest runs the same `SkillConfig` use case as the panel (`source = gitops:<commit8>`), the three-way compare uses the sha256 of the canonical rendering so comments and key order never create a diff, the repository wins, and a file with a problem is a per-file problem that stops no other and is never overwritten. The commit path restriction widens from `workflows/<name>.yaml` to also allow `skills/<name>.yaml`; `gitops_files` needs no new column (the path prefix tells the kinds apart). Write access to `.gru` is therefore the power to install skills from connected accounts and any public repository, the same as the admin gate, and the docs say so.
7. **Update check on demand; update is a separate confirmed step.** `POST /v1/skills:check` records `latest_sha`; `:update` moves the pin. No loop, no auto-update, no new interval variable: silently moving a pinned commit defeats the pin. With GitOps on an update is committed and reviewable.
8. **No history table.** One row per skill with a `version` counter for the optimistic lock; history is the audit log and, with GitOps, git.
9. **Skills apply only to the claude-code runner.** `gru-agent` has no skill loader, so the panel and docs say providers on that runner ignore them.
10. **Global skills were built, then removed on the owner's decision: skills are organization-level only.** The reserved-organization scope, `/v1/admin/skills*`, the Admin page and the always-on bundle merge are gone (migration `0022_skills_drop_global` deletes the rows); Gru's own skills live in its organization and are used by its automation. `stage.skills: []` means no skills.
11. **Roles and grants.** Any member lists; writes need an admin, owner or operator, or a member holding the `skills` grant (`GrantArea.SKILLS`, checked with `Principal.may_admin` in the use case).
13. **Script dependencies come from a wheelhouse stored with the skill (spec Decision 13, phase 12).** At install and update `gru-api` resolves a skill's Python dependencies (`uv.lock`, `poetry.lock`, `pylock.toml`, `requirements.txt`, `pyproject.toml` or a PEP 723 header) to binary wheels for `manylinux` amd64 and arm64 on Python 3.15, downloads them by hash and stores them with the skill (`org_skill_wheels`, migration `0017`); the bundle carries them and the agent verifies the digests, dry-runs the install offline and sets the `UV_*` variables so `uv run script.py` works with no network. `uv` ships in both the api and the task image. PyYAML is provided by the task image as a **temporary measure**, because Python 3.15 has no wheel for it yet; remove that when upstream ships one. A package with no binary wheel that the image does not provide is refused by name. Rejected: installing at task time (no network and no pip in the sandbox) and a compiler in the image.
14. **A marketplace plugin installs as one group of skills and agents (spec Decision 14, phase 13).** The admin gives repository, marketplace name and plugin name (the equivalent of `/plugin marketplace add` and `/plugin install`); gru pins the commit and reads `.claude-plugin/marketplace.json`. The plugin's `skills/*/SKILL.md` become catalog skills tagged with `plugin` and `marketplace` and its `agents/*.md` become `org_agents` rows (migration `0018`), written next to the skills by the agent; they update and uninstall together, and a single member skill cannot be updated or uninstalled alone (409). **Not loaded, and shown with the reason in the preview:** hooks (still refused, Decision 4), `.mcp.json` MCP servers (a stdio server would run code at start; a later decision), commands and everything else. An agent with `hooks` is refused, its `tools` and `model` need the same tick as `allowed-tools`, and a plugin with no skill is refused. Only a marketplace `source` that is a path inside the same repository is supported; any other is refused with a fixed sentence. Sources, grants (`skills`, no new area), audit (`skill.plugin_installed|updated|uninstalled`) and the size limits are those of skills. Plugin update and uninstall carry no optimistic-lock version (last writer wins, audited). GitOps: yes, `plugins/<name>.yaml` (`marketplace.repo`, `marketplace.name`, `plugin`, `sha`, `mode`), same canonical hash and applier (`SkillConfig.apply_plugin`); global plugins are not supported. A plugin's agents travel with its skills when any of them is in the task bundle, so `stage.skills` narrows by skill and takes the agents along. Rejected: loading plugin hooks and MCP servers now (arbitrary commands and processes), and plugin-level narrowing in `stage.skills` (a second mechanism).
15. **Bigger skills, and big archives live in the object store (Decision 15).** A skill may hold 1000 files and 50 MiB (one file at most 20 MiB) and a task bundle 100 MiB (was 200 files, 2 MiB, 8 MiB), so a whole repository root installs; wheels keep their caps (25 per skill, 20 MiB per skill, 40 MiB per task) and the agent's body bound stays bundle + wheels + agents. An archive up to 1 MiB stays inline in `org_skills.archive`; a larger one is put in the object store first (port `ISkillBlobStore`, adapter over the existing artifact `IArtifactBlobs`: same bucket, prefix and settings, no new `GRU_*` variable, key `skills/<org>/<name>/<sha>/<archive_sha256>.tar.gz`, global skills under the reserved org id) and the row keeps `archive_sha256`, `archive_size`, `archive_key` (migration `0019`, expand only; `archive` stays `NOT NULL` and holds an empty value). Reads fetch the object and check its sha256; `list` and `get` never load one. Delete, update, plugin replace and uninstall, and the organization purge (before its rows go, retried when the store fails) remove the objects, best effort outside the purge. With a database and no artifact bucket there is no object store and an archive over 8 MiB is refused with a fixed sentence. Over a limit the error says what to do (set the path to the skill's directory, not the repository root). Residual: the bundle builder still holds the archives of one task in memory (bounded by 50 skills of at most 50 MiB, and the 100 MiB cap refuses the task after unpacking). Rejected: a new bucket setting (frozen surface) and chunking archives in MySQL.
18. **Plugin skills are loaded through the plugin directory, so they are namespaced (`okf:validate`).** The bundle carries a plugin skill's files under `_plugins/<plugin>/skills/<name>/` and its manifest entry gains `"plugin"` (absent for other skills, so older bundles keep their bytes); the agent passes the directory with `--plugin-dir`. Spike on Claude Code 2.1.286: `skillOverrides` (`name-only`, `user-invocable-only`) are inert for plugin skills (only `on`, and `off` by not delivering, work), so gru refuses those two modes for them (`plugin skills only support the modes on and off`; legacy rows are delivered as `on`); the okf skills use sibling paths (`${CLAUDE_SKILL_DIR}/../validate/...`), so every skill of a plugin that is not `off` travels when any one is picked; bare `/validate` also resolves to the first plugin that has it, so catalog names stay unique per organization. `SkillOut` gains `plugin` and `marketplace` (additive, owner-approved).

# Consequences

- Additive surface approved on 2026-11-05: routes `/v1/skills*` (an `/v1/admin/skills*` set built first was removed with the global skills, Decision 10), the gateway route `/skills/v1/bundle`, six MCP tools (65 in all with the four plugin tools of Decision 14), the stage field `skills`, `GRU_SKILLS`, migrations `0015` and `0016`, the `skills/<name>.yaml` layout, six audit actions (29 in all) and the grant area `skills`. No metric series was added.
- No skill file content, archive or token is logged, counted or put in a commit message, audit event or error; log lines carry ids, names, 8-hex shas and byte counts.
- A skill is code the agent may run inside the gVisor sandbox with no network. The residual risk is the reason the catalog is admin-gated, pinned and audited, and why write access to `.gru` is documented as the same power as the admin gate.
- Not built: authoring a skill in the panel, a scheduled update check, plugins with hooks or MCP servers, global plugins, skills for the `gru-agent` runner, Claude API Agent Skills. The check on the real CLI (a skill listed in the `system/init` event, `mode: off`, `skills: []`, the GitOps round trip) needs the owner's cluster and key and is recorded as a manual item.
